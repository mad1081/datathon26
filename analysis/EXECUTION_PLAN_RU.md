## 2. Где должен выполняться inference

ТЗ требует выполнять все модели внутри сервиса команды, без передачи видео, кадров или описаний во внешние AI API. После предварительной загрузки весов обработка должна работать без исходящего интернета и переноситься во внутреннюю инфраструктуру банка.

Предлагаемая реализация: EC2 GPU → собственный Docker-контейнер → локально загруженные открытые веса → собственные UI и API. Вызов собственного процесса модели, даже по OpenAI-compatible протоколу, не означает вызов внешнего поставщика модели.

Это технически соответствует изложенной цели автономности. Прямого предложения «AWS EC2 разрешён» в ТЗ нет; окончательная трактовка организаторов не получена. Точная формулировка для них: «Допускается ли полностью автономный Docker-сервис с открытыми весами на арендованном EC2 GPU, без внешних AI API, работающий при отключённом исходящем интернете?» Это подготовленный вопрос; никому он не отправлялся.

Bedrock, Rekognition, облачные VLM/LLM и hosted inference для конкурсного видео не подходят под указанное ограничение. Отсутствие видимости этапа разработки для жюри само по себе не создаёт исключения из правил. Воспроизводимость офлайн проверяем реальным запуском с отключённым egress после кеширования весов, токенизаторов и необходимых GPU kernels.

## 3. AWS: уточнённый бюджет $5 000, параллельные эксперименты и отдельный inference

**Актуальное уточнение пользователя: все восемь моделей первой волны запускаются одновременно.** Сначала подготовить shortlist, evaluator и контейнеры; затем выделить каждой модели независимые GPU, выполнить прогоны на одинаковом dev-наборе, сохранить результаты и остановить экспериментальные EC2. Цель — получить сравнение как можно раньше. Ротация допускается для следующих экспериментов, но первая волна не ждёт очереди на одном сервере. Аренда на сутки не требуется; финальный сервис работает для жюри отдельно.

Предлагаемая конфигурация: **8 серверов, 12 GPU, 8 моделей одновременно**. Шесть `g7e.4xlarge` (каждый 1×96 GB VRAM, 128 GiB RAM) для шести небольших/средних кандидатов; один `g7e.12xlarge` (2×96 GB, 512 GiB RAM) для MiniCPM4.7 с проверенным tensor parallelism; один `g7e.24xlarge` (4×96 GB, 1 TiB RAM) для Qwen3.5-122B. Суммарно **$48.8472/час**, **$146.54 за 3 часа**, **$195.39 за 4 часа** вычислений. Нужна региональная квота 240 vCPU категории G/VT. Размещение — оценка с запасом, фактические VRAM/скорость ещё не измерены.

Альтернатива при доступной квоте P: два `p5en.48xlarge`, всего 16×H200 по 141 GB, 2 TiB RAM на сервер; $126.592/час и $379.78 за 3 часа. Для неё нужны 384 vCPU категории P. Это альтернативные конфигурации. Один P5en при выделении четырёх GPU крупной модели не позволяет запустить остальные семь моделей одновременно. Детали и назначения каждой машины — в [исследовании моделей](VIDEO_MODELS_RESEARCH.md).

**Оплата:** включённый EC2 оплачивается даже при нулевой загрузке. Обычный Linux On-Demand считается посекундно, минимум 60 секунд за запуск. Выход из SSH, завершение Python или остановка Docker не выключают EC2. После команды `Stop instance` обычные состояния stopping/stopped не тарифицируются за вычисления; сохранённые EBS-диски и Elastic IP могут продолжать тарифицироваться. Локальный instance-store NVMe стирается при остановке, поэтому сначала сохранить результаты в постоянное приватное хранилище. [Официальные правила AWS](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-lifecycle.html).

Два–три часа — целевое окно экспериментов, длительность уточняется по первым видео каждой модели. Все модели стартуют параллельно и независимо проходят проверку запуска. Для примера: 40 видео × 10 повторов = 400 задач на модель; при 30 сек/видео это 3 ч 20 мин, при 60 сек — 6 ч 40 мин на одном worker без настройки. Для десяти повторов за три часа нужны ≤27 сек/видео либо дополнительные реплики медленных моделей. Первую таблицу качества выдавать после одного полного прохода, затем обновлять статистику повторов. Усреднять метрики и измерять стабильность вердиктов; повтор одного ролика не создаёт новый независимый пример. Holdout не использовать для подбора.

Количество серверов определяется числом одновременно проверяемых моделей и временем повторов. Одна много-GPU машина может выполнять несколько независимых моделей, однако отдельно выключить оплату одной из её GPU нельзя. Объединение нескольких GPU для одной модели требует поддерживаемого runtime; сумма VRAM сама по себе не обеспечивает запуск.

Выделить финальному сервису отдельный On-Demand GPU worker и резервный worker с той же зафиксированной конфигурацией; не проводить на них эксперименты во время проверки жюри. Настройка и проверка переключения обязательны: наличие второй машины само по себе не даёт отказоустойчивость. Планировать минимум 24 часа работы после сдачи и не отключать по дедлайну автоматически. Экспериментальные машины останавливаются после сохранения результатов; диски продолжают тарифицироваться, пока существуют.

Бюджет $5 000 позволяет несколько коротких волн такого сравнения и отдельную работу финального сервиса. Предварительные потолки: до $2 500 на эксперименты, до $1 000 на финальный сервис/резерв и $1 500 нераспределённого запаса. Это лимиты планирования, не целевые расходы. Настройка окружений и загрузка весов на уже включённом сервере тоже входят в оплачиваемое время.

Практический первый шаг — квота. AWS документирует начальные GPU-квоты как 0 vCPU; действующая квота конкретного аккаунта может быть выше. Для основной первой волны нужно 240 vCPU категории G/VT. Баланс кредитов не повышает квоту автоматически. Проверить также поддержку EC2/EBS условиями конкретного кредита и доступность инстансов в выбранном регионе.

Источники: [G6](https://aws.amazon.com/ec2/instance-types/g6/), [G6e](https://aws.amazon.com/ec2/instance-types/g6e/), [G7e](https://aws.amazon.com/ec2/instance-types/g7e/), [квоты](https://docs.aws.amazon.com/ec2/latest/instancetypes/ec2-instance-quotas.html), [кредиты](https://aws.amazon.com/awscredits/).

У локального ноутбука RTX 4050 Laptop с приблизительно 6 GB VRAM. Он подходит для подготовки данных и приложения; доступные 48–96 GB заметно расширят выбор видео-моделей.

## 4. Какие модели сравнить

Первая волна: Qwen3.5-9B, Qwen3.8-27B, Qwen3-VL-32B-Instruct, MiniCPM-V-4_5, MiniCPM-V-4.7-35B-A3B, GLM-4.6V-Flash, Cosmos3-Nano (только Reasoner), Qwen3.5-122B-A10B. Ни одна из этих моделей пока не оценивалась на наших видео. Таблица ниже сохраняет компактные варианты и fallback для переноса финального сервиса.

BF16 — примерно 2 байта на параметр весов. Для 27B одни веса занимают около 54 GB; видеотокены, активации и служебные буферы требуют дополнительной памяти. Указанное размещение — оценка, не измеренный fit. На g7e.2xlarge системной RAM 64 GiB, поэтому загрузка должна быть потоковой/по шардам, без двух полных CPU-копий checkpoint. Blackwell требует совместимых driver/CUDA/PyTorch/kernels; при затяжной настройке продолжать compact baseline на L40S и FP8-кандидат.

Ни имя модели, ни публичный leaderboard пока не позволяют назвать победителя на этих кассовых действиях. Восемь кандидатов начинают параллельно; первый успешно прошедший весь pipeline становится временным baseline. Расширение вплоть до 30 экспериментов допустимо, если каждый опыт проверяет определённую гипотезу. 40 видео недостаточно для надёжного выбора по многократно подгоняемому одному набору. Дополнительный бюджет не устраняет model-selection overfit; holdout остаётся закрытым.

## 5. Как устроен анализ видео

`MOV → H.264 decoder → кадры с исходными timestamp → vision encoder → projector/resampler → визуальные + текстовые токены → language model → наблюдения/JSON`

Vision encoder разбивает кадры на патчи и получает эмбеддинги. Projector согласует размерность с LLM; resampler может сжать несколько кадров. Временные позиции и обучение на последовательностях помогают различать порядок действий. Поэтому VLM действительно может отвечать на вопросы о видео и выдавать JSON, но это не гарантирует точного обнаружения каждого действия.

Две минуты при 30 FPS — 3600 кадров. Выборка 2 FPS оставляет 240; короткий жест может попасть между ними. Большая модель не восстанавливает событие, которого не было во входных кадрах. Маленькие предметы также исчезают при уменьшении разрешения.

Стартовая гипотеза: перекрывающиеся временные окна на всём видео, затем более плотная проверка кандидатов. Отдельно сравнить с более плотной равномерной выборкой: второй проход не исправляет событие, пропущенное первым. Все цифры FPS/длины окон подобрать по измерениям, а не считать установленными оптимумами.

Выход модели сначала содержит наблюдаемые действия и моменты. Отдельный слой сопоставляет их с проверенным каталогом правил и допустимыми альтернативами. JPEG-доказательства извлекаются из оригинального видео; нормативные ссылки берутся из каталога, не генерируются моделью по памяти.

## 6. Предметная область и разметка

Основной источник — действующие правила кассовых операций НБРК №231 от 29.11.2019 с поправками. Кандидаты для проверки: пересчёт при клиенте, уход до окончания обслуживания, хранение ранее принятых денег, личные вещи работника, проверка инкассаторских сумок. Это гипотезы для просмотра, а не уже найденные классы датасета.

Нужны контрпримеры: телефон клиента может показывать цифровое удостоверение; пересчёт может быть машинным; начало операции может отсутствовать в ролике. Открытая дверь не доказывает отсутствие требуемой запирающейся двери. Другой сотрудник не обязательно неуполномоченный. Старые правила №58/2001 отменены. Договор другого банка полезен как контекст, но не становится внутренним регламентом Forte. Источники, пункты и ограничения доступа к актуальному тексту записаны в [DOMAIN_RESEARCH.md](DOMAIN_RESEARCH.md); перед финальной фиксацией повторно сохранить и проверить только используемые положения.

В разметке даны бинарный класс и отдельный таймкод. Нет типа нарушения, длительности, bbox или правила. 42 файла дают 40 уникальных видео, примерно 21 мин 40 сек. Для Х-4/Х-47 одинаковые байты, но разные таймкоды — 57 и 68 секунд. Оба сохраняем до проверки.

Агент подготовил локальную галерею всех 40 роликов. Для первой содержательной разметки нужен человек или запущенная самостоятельно VLM. Сейчас содержательный просмотр не выполнен. Планировать человеку около 45–60 минут на первичный проход и спорные моменты; автоматическая разметка после запуска GPU ускорит черновик, но не станет независимой истиной сама по себе.

## 7. Проверка качества и дополнительные данные

1. Группировать дубли и похожие постановочные сцены. Заморозить dev/holdout до подбора prompt и моделей; например, 28/12 уникальных роликов, если баланс/группы позволяют.
2. У holdout сохранять независимость: не переносить его примеры и ответы в prompts. Даже без обучения выбор модели и порога подгоняет систему под оценочный набор.
3. Smoke-test 2–4 dev-видео, включая длинное и отрицательное: декодирование, JSON, таймкоды, VRAM, полное время. Затем общий evaluator на одном dev-наборе для всех кандидатов.
4. Сохранять model revision, preprocessing, prompt/rule versions, video hashes, predictions, latency, peak VRAM, технические ошибки.
5. Сравнивать false positives/false negatives, локализацию, релевантность кадров, корректность источника и полный latency. ТЗ не задаёт числовой допуск таймкода — не придумывать его как официальный.
6. Одно видео в holdout из 12 меняет accuracy на 8.3 процентных пункта. Не заявлять надёжность 99% по такому объёму. Спорные метки учитывать отдельно, оригинал не переписывать.

Своя съёмка и синтетика разрешены FAQ, однако полезнее сначала снять несколько корректных/некорректных сценариев с другого угла после выявления конкретного пробела. Crop/яркость/resize дают проверки устойчивости, но не независимый test. Генеративное видео может искажать руки, купюры и порядок действий. Новое обучение на 40 роликах не является обязательным первым шагом.


## 8. Что именно строим и сдаём

UI загрузки MOV → FastAPI API с X-API-Key → очередь → GPU worker → правила/кадры-доказательства → результат с несколькими событиями.

- `POST /api/v1/analyze`: multipart `file`, возвращает `job_id`.
- `GET /api/v1/jobs/{job_id}`: `processing`, `done` или `failed`.
- Готовый результат: `job_id`, `status`, `verdict` (`violation`/`no_violation`), список `violations`.
- Каждое событие: `type`, `timecode_sec`, `description`, 1–3 `evidence_frames` с `timestamp_sec` и JPEG `image_base64`.
- Источник — в description по точной схеме и отдельным удобным представлением в UI.
- До 5 минут на видео, включая ожидание. Ошибка GPU/decoder/timeout становится `failed`, а не отрицательным вердиктом.
- Новая камера и новые видео; без аудио/идентификации лиц/зависимости от АБИС.
- Публичные UI/API, ключ жюри, инструкции, архитектура/модели, нормативные источники, поддерживаемые типы, ограничения и реальные ошибки. Питч 5 минут + 2 минуты вопросов для финалистов.

Основная метрика только за целый ролик даёт 25 баллов; локализация, тип и нормативное обоснование добавляют по 15. Выбирать модель только по бинарной accuracy недостаточно. Полная таблица приёмки всех требований и FAQ сохранена отдельно.
